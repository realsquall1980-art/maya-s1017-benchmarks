## 二、测试环境与口径

- 2x NVIDIA RTX PRO 5000 72GB (Blackwell), 73,415 MiB each；驱动 595.91.07；AMD Ryzen 9 9950X3D；249 GiB DDR5-6000 (dual-channel)
- Ubuntu 24.04, CUDA 13.0
- Project Maya v1.1.28 (commit 6afa525), build-1128/maya-ds4, sm_120
- Maya-S pack 348.4 GB, 25 files, 18/18 SHA-256 checks passed；混合 IQ2_XXS/IQ2_S/IQ3_S，2.56 bpw

**测速口径（六条，缺一条数字就不可比）：**

1. **一次只改一个结构旋钮**：TP 模式 → chunk 尺寸 → 上下文 / 分卡；opt-in 开关最后叠加在已定的结构上。
2. **只认引擎日志**：`prompt N tokens = … read in X ms (P tok/s), M generated in Y ms (D tok/s)`；不用端到端墙钟除 token（会把 prefill 和排队算进 decode）。
3. **prefill 只取 `0 reused` 的行**：`reused` 大的是缓存命中，不代表读入速度。
4. **冷热分开报**：重启后第一条是冷启动；decode 表用热值，冷值差异大时单独列出。
5. **decode 必须交错对拍**：A → B → A，每轮独立重启；**先停 unit、再清 `slots/`、最后起服务**（反序会被退出回写污染成假冷读）。
6. **质量门三件套**：15 题精确答案电池、三深度检索针、离线 `--ppl`（只在其有效范围内使用）。

## 四、机制：为什么这几个旋钮有效 / 无效

1. **真 TP2 是「加卡」方案，不是「拆两张卡」方案。** 总显存固定为 144GB 时，TP2 把每个专家劈成两半放两卡，能**完整**驻留的专家数反而下降（71.1/71.4% vs 74.5/74.9%），而 42K 提示词的流式字节翻倍（131.9 vs 63.5 GB）。上游那个 1.9× 是**9 张卡、`--tp 8`** 的数字——收益来自总显存变多。
2. **层切停在 19/21，是因为引擎自己解了最优。** `chunk>0 && groups>1` 时 `ds4_model.cu` 跑一段动态规划，目标是「最忙那张卡的流式字节最少」，解出来就是 GPU0 拿 0–18、GPU1 拿 19–39+head。手工给 20/20 等于把最优解改成次优（−4%）。
3. **chunk 16384 把块数减半**，热门专家被重复拉的次数变少：42K 提示词下 GPU0 流式 52.1 → 33.6 GB，prefill +8~11%（两对同条件读数的上下界；当轮记为 +9%）。chunk 32768 流式继续降（28.7 GB），但激活值把驻留从 72.2% 挤到 67.7%，把收益吃回去——**16384 是拐点**。
4. **缩窗口在这里换不到专家。** DeepSeek V4.1 的 KV 是压缩存法（FP4 + 滑窗）：512K → 256K 每卡只省 0.14 GB，约 +36 个专家（+0.3%），速度无差。常规模型「上下文减半能救显存」的经验在这里不成立。
5. **`REQUIRE_ALL_RAM` 已被 `auto` 覆盖。** `--mmap-experts auto` 启动时就把 CPU lane 的 4,317 个专家（47.6 GB）全拷进 RAM；strict 标志只是把「已经全进」变成「不全进就别起」，并且强制要求 `--mmap-experts off`。
6. **`PROMPT_SKIP=2` 是唯一真有收益、也真有代价的开关。** 它把第 20–39 层的早段保留行数从 2,668 行降到 128 行（即 DeepSeek 线上服务同款的 SWA bounded replay）。decode 完全不受影响，事实性召回在我们的探针里不变；但上游写明答案会「轻微漂移」——适合读长文/长代码，不适合要逐字可复现的写作。
7. **`RAM_SKIP_W` 打的是另一种形态。** 上游 +20~43% 是在 Maya-XS「专家全在 RAM」时测的；本机 72% 驻显存时，被跳过的正是不用搬的那部分，实测 0 收益，却白担质量风险。

## 五、质量门：三种工具只有两种能用

| 工具 | 本次实测 | 结论 |
|---|---|---|
| `--ppl FILE` | 基线两次逐位一致（4.0933 / 3.8300 / 3.7342 / 9.0713 / 7.0358 / 5.3583）；但 `RAM_SKIP_W=0.50`、`DS4_YOCO=0/2` 一字不变，而 `DS4_ATTN_MMA=0` 全变 | **假阴性**：对「少算一部分」的近似开关无效，只适合判数值路径改动 |
| 15 题精确答案电池 | 所有条件都是 14/15；唯一「错」是判分脚本不认下标 `H₂O` | 可用的下限门，灵敏度低 |
| 三深度检索针 | 44,480 token 提示词里埋开头（第 40 条）/ 正中（第 1,200 条）/ 尾部（第 2,395 条），3 个种子；精确档与 `PROMPT_SKIP=2` 均 **9/9 全对**；124K 针也答对 | 有效；**只问最后一条是假通过**——该开关保留的正是尾部行 |
| 固定 seed 文本相似度 | 基线自身三次两两相似度只有 0.318–0.417（温度 0 在 MoE + 批处理下并不确定） | **不可用**：跨条件相似度落在噪声里，不能用来证明「措辞没变」 |

## 六、测速方法学：三处会产出假数字的地方

1. **decode 顺序跑会造假**：同一序列里后测的那档看起来更快（冷首条 125–135，末轮 153–162）。交错 A→B→A 后，`PROMPT_SKIP` 的 decode 差异收缩到 ≤1%，才证明它不碰解码路径。
2. **会话缓存会让「冷读」变假**：`SLOT_KEEP=1` 时引擎退出会把会话写回 pack 的 `slots/`。先删目录再停进程 → 下一轮测出 0.5 秒读完 44K token 的假冷读。正确顺序是**先停 unit → 再清 slots → 再起**。
3. **短提示词的 prefill 不是能力上限**：51 token 的请求只有 90–200 tok/s，因为固定开销占大头；要判 prefill 必须看 ≥2K、尤其 42K/124K 的 `0 reused` 行。

另有一条**引擎开关命名坑**：直接跑引擎二进制时必须写 `STRATA_DS4_*`；`MAYA_DS4_*` 只在服务端经 `maya_names.alias_env` 转换后生效，直连二进制写 `MAYA_` 名会被**静默忽略**（我们第一轮 PPL 全部「无差异」就是这个原因）。

## 八、限制（诚实清单）

- **L1 快速对照不是统计 A/B**：每个条件 1 次启动、2 条 42K + 3 条代码 + 3 条散文 + 15 题电池。终选结构 R3 累计 6 次独立启动（3,638–3,722，跨度 ±1.4%），所以 ±3% 以内一律判噪声。
- **L2 只测单请求单轮**（`0 reused`）：未测并发、多轮长对话 KV 复用、视觉、工具调用；不是公开榜单基准。
- **L3 未压满窗**：本轮最长 124–131K；512K/1M 的窗口行为见 10-22 那篇；YaRN×16 外推下「读得到」≠「与 64K 内同等锐利」。
- **L4 `PROMPT_SKIP=2` 的文风漂移未量化**：事实召回与短答正确性有证据，长文措辞可复现性没有证据；上游也写明会「shift a little」。
- **L5 机器特异**：9950X3D 双通道 DDR5-6000、16 个 CPU lane 线程决定了 offload 上限；要抄的是旋钮顺序，不是驻留数字，先在自己的机器上跑校准。
- **L6 未跑上游标准协议**：`strata bench` / `--report` 未用；DSpark 增益是 1.1.20 校准结果，未在 1.1.28 重测。
